# ADR: Identity Server Migration — Azure App Service to AWS ECS Fargate

**Status:** Proposed
**Owner:** Staff DevOps Engineer
**Supporting evidence:** every non-obvious call below is sourced and dated in the [migration decision log](./docs/decision-log.html) (also committed as `docs/decision-log.html`) — decision IDs (D1, D3, …) referenced throughout this document link back to the finding and rationale there.

## Context

The Identity Server handles authentication and token issuance for every StrongMind product. It's currently the last major production workload not on AWS: a .NET 6 app on Azure App Service (Linux), backed by Azure SQL Database and Azure Key Vault, at ~400 req/min sustained and ~1,200 req/min peak during the 7–9 AM Mountain Time school-start window. Everything else StrongMind runs is already on ECS Fargate.

That split is costing more than infrastructure diversity:

- **Two operational models for one platform.** IAM, secrets, networking, deployment, and observability all exist twice — once for "most of AWS" and once for this one Azure service — which is exactly the kind of blind spot behind the on-call complaint that "I can't tell if something is wrong until a customer calls." The Identity Server isn't yet wired into the CloudWatch-based observability this org is standardizing on (Part 4).
- **A legacy directory dependency that doesn't need to exist.** The service calls Azure AD Domain Services for directory lookups. As detailed in D1, there's no clean way to bridge that into AWS (Simple AD is retired to new customers and never supported trusts; Azure AD Domain Services doesn't support trusts either), and the underlying need — user/group lookups — is almost certainly better served by a direct Entra ID API call than by any directory infrastructure at all.
- **This is the highest-blast-radius service to leave stranded.** Every other product (the Rails LMS, the PowerSchool integration) depends on it for auth. A migration plan needs to be conservative about downtime and explicit about rollback, not just about "getting it onto Fargate."

## Decision

Containerize the Identity Server as a Linux container and deploy it to the **existing** `strongmind-production` ECS Fargate cluster and VPC — not a new one — consistent with how the rest of the platform already runs. Migrate the database to RDS for SQL Server via a scheduled bacpac-based cutover (not continuous replication — see D8), migrate secrets to AWS Secrets Manager, and cut traffic over with a compressed Route 53 weighted-routing ramp (D3) that runs inside the same maintenance window as the database cutover, not across days. Replace the Azure AD Domain Services dependency with a direct Entra ID (Microsoft Graph) call where the code allows it in this timeframe; where it doesn't, keep the cross-cloud call as documented, monitored tech debt rather than standing up parallel AD infrastructure (D1).

**This is explicitly not a zero-downtime migration, and that's a deliberate choice, not an oversight:** new logins and token issuance are unavailable for a short, scheduled, overnight maintenance window (see Traffic Cutover Strategy). The tooling available for this specific source/target pair (D8) doesn't support a live database cutover, and claiming zero-downtime anyway would mean the on-call engineer discovers the gap during the actual migration instead of reading it here first.

That last hedge is only useful if it resolves to a concrete answer instead of an open-ended assumption — this exercise doesn't include the actual Identity Server codebase, so "where the code allows" is scoped by an audit, not asserted:

- **Week 1 of the migration, before the cutover window is scheduled:** an engineering spike audits every AADDS call site and classifies each as either a logical lookup (user/group existence, membership — portable to a Graph API call) or a genuine LDAP/Kerberos/NTLM bind that Graph can't serve. This is what turns "where the code allows" into an actual list instead of a guess.
- **For whatever remains genuinely LDAP-bound at cutover:** the interim path is AADDS's own "secure LDAP external access" feature — LDAPS on port 636 over the internet, TLS via a certificate from a public CA (StrongMind's own domain, not the default `.onmicrosoft.com`, which can't get a public-CA cert), locked down by an Azure NSG rule to a single allowed source: the fixed Elastic IP of the NAT Gateway the ECS tasks egress through. Enabling public LDAPS without that NSG lock is a real brute-force exposure — the lockdown isn't optional hardening, it's the thing that makes this an acceptable interim path at all.
- **This is tracked as time-boxed tech debt, not indefinite:** a follow-up ticket, owned, targeted for removal within one quarter of cutover — not a permanent cross-cloud dependency that quietly outlives the migration project that created it.

> **Assumption:** the Identity Server joins the same VPC/ECS cluster already hosting the Rails app (`strongmind-production`, per the Part 2 assumptions), rather than a new VPC. This reuses existing subnets, NAT/VPC endpoints, and security-group patterns instead of building networking from scratch.

## Migration Architecture

**ECS Fargate task definition.** One task per service replica: **1 vCPU / 2 GB memory** — .NET 6 Kestrel apps handling RSA/ECDSA token signing are more CPU-bound per request than a typical CRUD API, so this errs toward CPU headroom rather than the smallest viable size. Baseline capacity min **3** / max 6 tasks spread across **3 AZs** — with only 2 tasks, losing a single AZ can leave exactly one task standing for a service everything else depends on; 3 tasks across 3 AZs means an AZ failure still leaves 2 tasks (~two-thirds capacity) while target tracking reacts to backfill the rest, rather than a single point of failure disguised as "multi-AZ." Application Auto Scaling target-tracking on `ECSServiceAverageCPUUtilization` at **60%** as the reactive layer, 60s scale-out cooldown / 300s scale-in cooldown. Deployment configuration: `minimumHealthyPercent: 100`, `maximumHealthyPercent: 200` (never drop below current capacity mid-deploy), with the deployment circuit breaker + automatic rollback enabled per D2. ALB target group health check against **`/health/ready`** (not a bare liveness check) every 15s, 5s timeout, healthy threshold 2, unhealthy threshold 3 — split from a separate `/health/live` via ASP.NET Core's tagged health checks (`Predicate = check => check.Tags.Contains("ready")`). The distinction matters here specifically: liveness should only ever answer "is the process alive," never a dependency, or a brief DB blip turns into every task getting killed and restarted at once. Readiness is where the DB connection and the directory dependency (AADDS or Graph, per D1) get checked — that's the actual "should this task receive auth traffic right now" question, and routing traffic away from a task whose dependency is unhealthy is exactly the kind of signal that was missing when the on-call engineer said they "can't tell if something is wrong until a customer calls." (This liveness/readiness split is specific to the Identity Server's .NET health-check middleware; the Rails application's equivalent health-check story — and where it's intentionally simpler — is documented in `OBSERVABILITY.md`, not duplicated here.)

Target tracking alone reacts to load that's already arrived — a Fargate task still has to pull the image, boot, and pass two consecutive 15s health checks before it takes traffic, so waiting for CPU to cross 60% right at 7:00 AM means serving the front edge of the spike understaffed (D9). Since the 7–9 AM Mountain Time spike is a known, recurring pattern rather than random variance, it gets a **scheduled scaling action** layered on top of target tracking, not instead of it: `application-autoscaling put-scheduled-action` raises `MinCapacity` from 3 to 5 at **6:15 AM**, and a second scheduled action drops it back to 3 at **9:15 AM** — a 45-minute lead-in for task startup plus a 15-minute trailing buffer past the stated peak window, Monday–Friday only. Both actions are declared with `--timezone "America/Denver"` rather than a fixed UTC offset, specifically so the schedule doesn't silently drift by an hour at the DST transitions each spring and fall. Target tracking still governs everything above that floor — if an unusually heavy morning pushes past what the pre-scaled 5 tasks handle, it scales on out to the max of 6.

**RDS for SQL Server.** SQL Server Standard Edition, engine version matching SQL Server 2019 compatibility level to match the source. Multi-AZ deployment (this is auth infrastructure — a single-AZ database is not an acceptable single point of failure for a service everything else depends on). Sized initially at `db.r6i.large` as a starting point given the traffic profile, with storage autoscaling enabled; right-sized after the rehearsal migration in D8 shows actual data volume and query load.

**On cost, said plainly rather than left implicit:** RDS for SQL Server Standard Edition carries a commercial per-vCPU license cost Azure SQL Database's PaaS pricing bundles differently — Multi-AZ roughly doubles that license cost on top of the compute itself. Two cheaper-sounding alternatives were considered and rejected, not overlooked:
- **Migrating the engine to RDS for PostgreSQL** (matching what the Rails app already runs) would eliminate the SQL Server license entirely, but that's an engine migration, not a cloud migration — a separate, larger initiative with its own schema/query-compatibility risk, and the prompt scopes this migration to "RDS (SQL Server)" specifically. Worth raising as a future option once this move is stable, not bundling into it.
- **Staging through Azure SQL Managed Instance** was considered as a way to get a DMS-CDC-capable source (unlike Azure SQL Database, DMS does support Managed Instance as a CDC source) — but that adds an entire extra migration hop (Azure SQL Database → Azure SQL Managed Instance → RDS) and timeline for a benefit the freeze-window approach in D8 already achieves without it. Accepting a short, honest maintenance window once is cheaper than staging through more Azure infrastructure to avoid one.

Staying on SQL Server, at this cost, is the accepted tradeoff for this migration — the goal is getting off Azure, not re-litigating the database engine at the same time.

**Secrets Manager.** Everything currently in Key Vault (DB connection string, the token-signing certificate, any third-party API keys) moves to Secrets Manager as individual secrets, referenced in the ECS task definition's `secrets` block (fetched by the task execution role at launch, injected as environment variables — never baked into the image or task definition in plaintext). Two things get handled deliberately rather than by default:
- **The signing certificate does not get rotated as part of this migration.** The exact same certificate moves over. Rotating signing keys and migrating clouds in the same change would make it impossible to tell which one caused a token-validation failure if something breaks, and every already-issued token would need to survive the cutover.
- **DB credentials** use Secrets Manager's native rotation (AWS-provided Lambda rotation template for SQL Server) once the migration itself is stable — not enabled during the cutover window itself, to keep that period free of unrelated moving parts.

**VPC/networking.** ECS tasks and RDS live in private subnets across the same AZs the existing production cluster already spans; only the ALB sits in public subnets. Security groups are chained tightly: ALB SG accepts 443 from the internet; the ECS task SG accepts traffic only from the ALB SG on the container port; the RDS SG accepts 1433 only from the ECS task SG. Interface VPC endpoints for ECR (API + DKR), Secrets Manager, and CloudWatch Logs, plus a gateway endpoint for S3, so routine task traffic (image pulls, secret fetches, log delivery) never needs a NAT Gateway or a path to the public internet. The NAT Gateway isn't removed, though: the Microsoft Graph API calls and the interim public LDAPS path to AADDS (below) are both genuine internet egress, and the NAT Gateway's fixed Elastic IP is exactly what gets allowlisted on the Azure NSG side for the LDAPS path — VPC endpoints cover AWS-internal traffic, NAT covers the two Microsoft-facing dependencies that still need it.

**IAM — least privilege, specifically:**
- **ECS task execution role:** `ecr:GetDownloadUrlForLayer`/`BatchGetImage`/`GetAuthorizationToken` scoped to the specific ECR repository ARN; `secretsmanager:GetSecretValue` scoped to the specific secret ARNs this service uses (not `*`); `logs:CreateLogStream`/`PutLogEvents` scoped to this service's log group.
- **ECS task role** (used by the running app, not by ECS itself): only what the .NET app needs at runtime — CloudWatch `PutMetricData` and X-Ray `PutTraceSegments` for Part 4's observability work. No broad AWS access by default.
- **GitHub Actions OIDC role** (already referenced in `rails-deploy.yml`, reused for the Identity Server's own deploy workflow): `ecs:RegisterTaskDefinition`, `ecs:UpdateService`, `ecs:DescribeServices`/`DescribeTaskDefinition` scoped to the specific cluster/service ARNs, `ecr:*` push permissions scoped to the specific repository, and `sns:Publish` scoped to the single ops-alerts SNS topic ARN (the pipeline's own failure-notification step, not broad SNS access). Critically, **`iam:PassRole` is restricted to the exact task execution/task role ARNs** — an unscoped `PassRole` would let a compromised workflow attach a more privileged role to a task, which defeats the rest of this list.

## Traffic Cutover Strategy

Route 53 weighted routing across health-checked records for the Azure App Service and the new ALB (D3), **compressed into the same maintenance window as the database cutover** rather than run as a multi-day gradual shift — because the two databases can't both be authoritative at once without continuous replication, which isn't available here (D8).

**Expected user impact:** new logins, refresh-token exchanges, and other write/token-issuance endpoints return 503 for the duration of the freeze-through-ramp window (overnight Mountain Time, on the order of minutes). Already-issued access tokens keep validating throughout — that's a signature check against the public key, not a database call — so active sessions don't drop, only new authentication does. This is the honest cost of the "short maintenance window" framing in D8; it's called out explicitly here so it isn't discovered as a surprise against the traffic path described above. Sequence, in order:

1. **Pre-stage (days ahead, zero production risk):** rehearsal bacpac export/import to validate the target schema and surface issues early (D8). **At least 48 hours before the window,** the DNS record's TTL drops to 60s. Lowering it the night of does nothing — resolvers and clients that already cached the old, longer-TTL answer keep using it until that cached TTL expires on its own, regardless of what the new record says. The compressed ramp in step 5 only works if caches have already expired by then.
2. **Maintenance window opens (scheduled overnight Mountain Time — nowhere near the 7–9 AM peak):** hard write-freeze on the Identity Server — a maintenance-mode flag returning 503 on login/token-issuance endpoints (or a read-only DB role), not just "pause deploys." **This freeze holds on both clouds for the entire ramp below, not just until step 4.** Azure SQL and RDS are never simultaneously writable — there is exactly one writer at any moment between here and step 5's completion. **The Route 53 health checks driving this whole sequence deliberately don't hit the endpoints the freeze affects:** the Azure-origin check hits `/health/live`, which only reflects whether the process is up — it doesn't care that login/token endpoints are returning 503, so the freeze itself can never flip Azure "unhealthy" and force an unplanned early shift to AWS. The ALB-origin check hits `/health/ready`, which reflects real dependency health (DB, directory) rather than the freeze — so it stays 200 through a normal freeze, and only goes unhealthy (correctly triggering the rollback in step 6) if something is actually wrong with the new environment.
3. **Final DB sync + validation:** final bacpac export/import, row-count and `CHECKSUM_AGG`/`BINARY_CHECKSUM` validation per table, spot-checks on the users/persisted-grants tables.
4. **Point ECS at RDS** via the now-migrated Secrets Manager connection string. Azure remains frozen — it is not yet re-enabled as a writer at this point, even though it's still receiving 90–100% of live traffic.
5. **Compressed Route 53 ramp:** 10% → watch ALB 5xx rate and p99 latency for a few minutes → 50% → watch again → 100%. Minutes, not days. **The freeze does not lift until weight reaches 100% AWS.** Until then, the fraction of traffic still landing on Azure is served against a frozen, read-only Azure SQL — not a live one — which is the only way two clouds can be in the traffic path at once without two writers.
6. **Rollback trigger:** if the AWS-side Route 53 health check goes unhealthy, or ALB target 5xx rate / p99 latency breaches the Part 4 alarm thresholds during the ramp, revert weight to 100% Azure immediately (a DNS-only change) **and lift the freeze on Azure in the same action**, restoring it as the single writer. Any write that reached RDS during the aborted ramp is now stranded and needs manual reconciliation back into Azure — the same class of problem as the bake-period risk below, just bounded to a few minutes instead of 24–48 hours.
7. **Freeze lifts on AWS, and only on AWS,** once weight reaches 100% and the rollback trigger hasn't fired. RDS is now the single writer.
8. **Bake period (24–48h):** Azure stays frozen and idle at 0% weight as a rollback option — kept read-only, not resynced, not serving traffic. This is explicitly **not** a clean rollback window after the first few minutes of real traffic on AWS: any write that lands on RDS during this period can't be cleanly reverted to Azure without manual reconciliation (see Risk Register). The bake period is for confidence, not for treating rollback as free.
9. **Decommission:** after the bake period and stakeholder sign-off, tear down the Azure App Service and Azure SQL Database.

**In-flight requests at each weight change:** a weight shift only changes which origin a *new* DNS resolution returns — a request already connected to Azure (or AWS) when the weight moves completes normally against that origin. Nothing gets forcibly cut off mid-request; the freeze/single-writer discipline above is what actually prevents data divergence, independent of and in addition to the DNS propagation lag itself.

## Database Migration Plan

**Tooling:** `sqlpackage` bacpac export/import — Microsoft's own sanctioned mechanism for moving data out of Azure SQL Database (PaaS). Two things ruled this out as a default before it became the plan, both confirmed against primary sources (D8):

- **AWS DMS cannot do this as continuous replication.** AWS's own DMS documentation states plainly that DMS doesn't support CDC operations with Azure SQL Database as a source — full-load only. This eliminates the "stand up DMS with ongoing replication for a live cutover" approach that would otherwise be the default answer.
- **RDS's native backup/restore path (via S3) isn't available either**, because Azure SQL Database (the PaaS tier, not Managed Instance) doesn't expose native `BACKUP DATABASE` — its backups are fully automatic and system-managed.

Bacpac is best-practiced for databases under 200GB; an identity/auth database (users, clients, grants/tokens — not transactional application data) is almost certainly well inside that, which is confirmed during the rehearsal runs rather than assumed.

**Validation approach:** row counts per table, `CHECKSUM_AGG(BINARY_CHECKSUM(*))` per table compared source vs. target, and manual spot-checks on the highest-consequence tables (users, persisted grants/tokens) for referential integrity and identity-column continuity.

**Minimal-downtime handling given the 400 req/min baseline:** the write-freeze window only needs to cover one final bacpac cycle of a small database, scheduled overnight outside the 7–9 AM peak — the realistic freeze is expected to be on the order of minutes, not hours. This is deliberately framed as a short, honest maintenance window rather than an overclaimed "zero-downtime" migration the tooling can't actually deliver at the database layer.

## Risk Register

| # | Risk | Likelihood | Impact | Mitigation |
|---|------|------------|--------|------------|
| 1 | Post-bake-period rollback requires manual reconciliation, not a clean revert — a write on AWS after the ramp can't be un-done by flipping DNS back | Medium | High | Keep the freeze/validation/ramp sequence tight; run automated smoke tests immediately after 100% cutover, before declaring success; document explicitly that rollback after the first few minutes of live AWS traffic is forward-fix, not revert |
| 2 | Downstream callers (Rails LMS, PowerSchool integration) break due to environment differences that don't show up until real traffic hits AWS — e.g., an IP allowlist on the PowerSchool side scoped to Azure's egress ranges | Medium | High | Confirm the public hostname doesn't change (Route 53 handles this); audit whether PowerSchool's integration allowlists by IP vs. hostname well before the maintenance window; coordinate the cutover window with the PowerSchool integration owner |
| 3 | Token signing certificate mismatch invalidates already-issued tokens across every product that validates them | Low | High | Migrate the exact same certificate rather than rotating during the move (see Migration Architecture); diff the JWKS endpoint output pre- and post-migration as an automated pre-cutover check |
| 4 | .NET 6 on Azure App Service and .NET 6 on ECS Fargate behind an ALB make different assumptions about the request pipeline — most commonly, forwarded-header handling for client IP/scheme | Medium | Medium | Explicitly configure ASP.NET Core's forwarded-headers middleware to trust the ALB, matching what Azure App Service's front end did implicitly; verify in a pre-production ECS environment against real ALB traffic before the cutover window, not for the first time during it |
| 5 | .NET 6 reached end of support in November 2024 — already out of support today, not a future concern. Not addressed by this cloud migration, and easy to let quietly stay unaddressed since the migration "worked" | Medium | High | Track runtime upgrade as explicit, owned follow-up work, decoupled from this migration's change window (don't bundle a cloud move and a runtime upgrade into one rollback surface). Target **.NET 10 LTS** directly, not .NET 8 — .NET 8 and .NET 9 both reach end of support November 10, 2026, so landing on .NET 8 now just schedules the same problem a few months out |

## Definition of Done

- 100% of production traffic routed to AWS (Route 53 weight: Azure = 0%) for the full agreed bake period with no manual intervention required.
- ALB target-group error rate and p95/p99 latency at or better than the pre-migration Azure baseline over that same window.
- RDS data validation (row counts + checksums) shows zero discrepancies against the Azure SQL Database snapshot taken at freeze time.
- JWKS/signing-key output confirmed identical pre- and post-migration; zero authentication failures attributable to signature mismatches.
- Downstream consumers (Rails LMS, PowerSchool integration) show no elevated error rate correlated with the cutover.
- Zero remaining references to Azure Key Vault in application configuration; all secrets resolved from AWS Secrets Manager.
- Part 4's CloudWatch alarms are live against the new service and have been verified to fire correctly (via a controlled test) before Azure is decommissioned.
- Azure App Service and Azure SQL Database formally decommissioned, with billing confirmation that they've stopped incurring cost.
